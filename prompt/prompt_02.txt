# 中文书写能力扩展项目实施计划书

**项目名称：** 基于 React、SVG、GSAP 与 Three.js 的中英文混合艺术签名系统扩展

**项目目标：** 在保留现有英文书写效果的基础上，建立支持约 3500 个一级常用简体汉字、数字、常用中英文标点及中英文混排的中文书写引擎，实现完整笔画逐笔显现、3D 铅笔沿中线同步运动、响应式排版、可靠的字形数据管理及全面的自动化质量验收。

## 一、项目总体目标与基本原则

### 1.1 核心建设目标

1. 保留现有英文引擎、英文单线书写机制和已经通过的测试，不进行无必要的大规模重写。
2. 新增中文完整笔画轮廓、真实笔顺、中线轨迹、动态遮罩及艺术化签名表现。
3. 支持数字、常用中英文标点和空格，允许中英文混合输入。
4. 建立约 3500 个一级常用简体汉字的覆盖与验收目标，以实际合格字形数量作为最终统计依据。
5. 建立可追溯、可复验、可扩展的本地字形数据系统，不依赖运行时在线 API。
6. 完成从输入预检、字形加载、排版、书写、清除、异常恢复到生产环境验收的完整闭环。

### 1.2 不可妥协的原则

- 真实笔顺优先，艺术化调整不得破坏基本笔画结构和书写顺序。
- 完整笔画轮廓、中线轨迹和动态遮罩必须正确匹配。
- 3D 铅笔笔尖、笔画显现和对应阴影必须共享统一的动作进度。
- 未通过质量门禁的字形不得进入正式字库。
- 输入校验失败时不得静默删除、替换或改写用户输入。
- 新增中文功能不得破坏已有英文测试。
- 性能优化不得牺牲真实笔顺、完整笔画和笔尖同步。
- 所有正式发布结论必须由实际测试结果支持，不得以计划执行代替验收通过。

## 二、总体技术架构

### 2.1 字符引擎分层

按照字符类别分别处理字形，通过统一接口转换为标准书写计划。

| 模块 | 主要职责 |
|---|---|
| 英文引擎 | 沿用现有原创单线字形、轨迹和连笔机制 |
| 中文引擎 | 管理完整笔画轮廓、中线、笔顺、动态遮罩及字形元数据 |
| 数字与标点引擎 | 提供经过验证的专用单线字形和书写顺序 |
| 排版引擎 | 处理字符宽度、留白、基线、换行、行间距及整体居中 |
| 字形数据管线 | 完成数据源转换、质量检查、异常隔离、修复复验和分片构建 |
| 字形加载与缓存 | 管理本地数据分片、按需加载、解析结果及 LRU 缓存 |
| SignatureController.js | 统一协调书写计划、动作进度、GSAP 时间线、异常恢复和清除流程 |
| SVG / Canvas / Three.js | 分别负责完整笔画显现、辅助遮罩或粒子效果、3D 铅笔及相关场景渲染 |
| 测试与验收系统 | 执行自动化测试、视觉回归、同步测量、性能检查及报告生成 |

### 2.2 统一书写计划

所有字符引擎必须输出统一格式的有序动作段。每个动作段应提供共享局部进度，并包含完成执行所需的轨迹、时间参数、坐标映射和动作类型。

动作类型至少包括：

- 笔画书写。
- 字内抬笔。
- 字间移动。
- 换行移动。
- 落笔与收笔。
- 必要的辅助视觉效果。
- 清除和粒子消散。

`SignatureController.js` 是统一协调入口。各渲染模块不得自行决定字符顺序、换行位置或独立计算动画进度。

### 2.3 统一坐标契约

本计划建议采用统一逻辑坐标系，并保持字形原有宽高比例。

每个字形独立保存前进宽度、左右留白、基线偏移、边界和视觉修正参数。完整笔画、中线及相关几何数据共享一致的坐标变换。

坐标处理分为三个层次：

1. 字形局部坐标。
2. 文本排版坐标。
3. 当前视口和 Three.js 场景的渲染坐标。

窗口缩放时同步更新渲染映射，不改变当前书写任务已确定的字符顺序、换行结果和动作计划。

## 三、字形数据源与标准化系统

### 3.1 数据源选型

原型阶段对 Make Me a Hanzi 与 Hanzi Writer Data 进行同组对比，比较项目包括：

- 目标汉字覆盖率。
- 代表性字形的完整轮廓质量。
- 笔画中线的可用性及匹配程度。
- 笔顺和轨迹连续性。
- 复杂笔画的转换与修复成本。
- 动态显现效果和笔尖同步表现。
- 数据源许可、来源版本及使用条件。

根据统一指标选定主数据源，另一套作为受控备用来源。最终选择必须以实际测试和许可核查结果为依据，不预先假定任何来源已经完全满足要求。

### 3.2 构建阶段统一转换

建立离线字形数据处理流水线，将选定来源转换为统一内部格式。

每个标准字形至少保存：

- 字符及编码信息。
- 数据源、版本、许可和来源追踪信息。
- 按真实笔顺排列的笔画序列。
- 每笔完整轮廓和对应中线轨迹。
- 统一的局部坐标、边界及几何度量。
- 前进宽度、左右留白、基线偏移和视觉修正参数。
- 自动检查结果、修复记录、评分和人工复核结论。
- 最终质量状态及进入正式字库的依据。

原始数据中不存在的属性必须经过可靠的转换或推导流程获得，不能仅凭字段补齐就认定数据合格。

### 3.3 中线生成与修复

采用原始中线优先、自动推导辅助、疑难字形人工复核的策略。

处理流程如下：

1. 读取原始轮廓和中线。
2. 检查轨迹连续性、起终点、坐标对应关系和轮廓匹配。
3. 对确定性问题尝试自动修复。
4. 对缺失或不合格的中线尝试自动推导。
5. 对候选结果重新执行几何检查、动画抽测和笔尖同步验证。
6. 疑难字形进入人工复核。
7. 不合格字形隔离，不进入正式字库。

中线位于轮廓内部并不等于符合真实笔顺。自动生成的中线必须有独立的质量验证依据。

### 3.4 双源候选择优

采用风险分级比较。

原型阶段完整比较两套来源的代表性字形。全量阶段先处理主数据源，对缺失、质量不合格、修复失败、复杂度较高或动画抽测异常的字形生成备用候选。

对已经通过自动检查的主来源字形进行代表性抽样审计，以发现自动检查的系统性漏检。

候选选择分为两个阶段：

- **硬性质量门禁：** 不合格候选直接淘汰。
- **合格候选择优：** 综合比较轮廓、中线、笔顺、轨迹连续性、同步误差和排版表现。

质量相近时优先采用主数据源。不得未经验证地混配不同来源的轮廓与中线。

## 四、字符覆盖与输入预检

### 4.1 首期字符范围

首期目标包括：

- 约 3500 个一级常用简体汉字。
- 数字 `0–9`。
- 基础英文标点。
- 常用中文标点，包括逗号、句号、顿号、问号、感叹号、分号、冒号、单双引号、圆括号和常用书名号。
- 英文字母、空格、中英文混排及用户明确输入的换行。

其他符号采用分级扩展机制。只有完成字形数据、书写顺序、宽度规则和动画测试后，才可加入正式白名单。

### 4.2 输入校验原则

输入校验必须以正式字形注册表为依据，而不是仅使用宽泛的字符正则表达式。

预检失败时：

- 列出全部问题字符。
- 显示从 1 开始的用户可见字符位置。
- 给出易理解的拒绝原因。
- 保留原文，不自动删除或替换字符。
- 开发日志记录相应 Unicode 码点和详细错误信息。
- 恢复输入框及提交能力。

仅统一必要的换行符表示，不修改空格数量、标点、字符顺序和用户明确输入的换行。

### 4.3 预检与加载状态

预检期间锁定输入框，提交按钮显示轻量加载状态。

预检成功后开始书写；预检失败后恢复输入，保留原文并显示错误信息。

字形数据分片必须从本地加载，运行时不依赖在线 API。

## 五、响应式输入与文本排版

### 5.1 输入交互

将现有输入框调整为响应式 `textarea`。

- 桌面端正常输入时，Enter 提交。
- 桌面端 Shift+Enter 换行。
- 中文输入法处于组合输入状态时，Enter 交由输入法处理。
- 手机端 Enter 插入换行，圆形按钮负责提交。
- 输入框达到合理高度后在内部滚动。
- 签名区域独立执行自动换行。
- 通过自动化测试覆盖不同浏览器的 IME 事件行为。

### 5.2 字形排版

每个字形独立保存排版参数，包括前进宽度、左右留白、基线偏移和必要的视觉修正。

每行采用统一基线和行高，同时保留字符类别及单字垂直偏移规则。

自动换行遵循以下原则：

1. 优先单行显示。
2. 达到字号可读性下限后自动换行。
3. 结合字形宽度与中文标点断行规则，避免不自然的标点位置。
4. 用户明确输入的换行必须保留。
5. 所有行整体居中，按自然顺序逐行书写。
6. 排版完成后生成固定布局结果，供全部渲染模块共享。

### 5.3 文本长度与安全上限

不直接拍定固定字符数或动画时长上限，而是根据原型测试建立可配置的安全预算。

综合评估：

- 字形可读性和最小字号。
- 自动换行后的最大合理行数。
- 实际笔画数量及复杂度。
- 预估动画时长。
- 设备性能与内存占用。

预检阶段完成任务规模评估。超过安全范围时保留原文，明确提示原因，不自动截断。

## 六、中文书写动画与视觉效果

### 6.1 完整笔画显现

中文采用完整笔画轮廓逐笔显现，而非简单地让一条细线代替最终墨迹。

每笔通过动态遮罩逐渐揭示完整形状。3D 铅笔沿对应中线运动，尽可能使墨迹显现位置与笔尖同步。

对于不同字形，可以根据实际轮廓和中线匹配情况，使用 SVG 或 Canvas 辅助遮罩，但必须服从统一坐标和共享动作进度。

### 6.2 混合时序

以中线轨迹长度为基础时长，再结合以下因素进行修正：

- 笔画类型和长度。
- 曲线复杂度与转折。
- 起笔、收笔和倾斜动作。
- 字内、字间和换行抬笔类型。
- 字符类别及整体动画时长预算。

先通过代表性原型校准速度、时长和缓动参数，再冻结正式标准。

### 6.3 铅笔、阴影与抬笔

铅笔保留轻微落笔、收笔和倾斜动作，以笔尖为旋转参考点，不破坏轨迹同步。

阴影根据字内、字间和换行三种抬笔动作，调整柔和度、透明感和位置。

所有效果必须由统一协调层调度，不允许各模块分别使用不一致的进度计算。

### 6.4 清除与签名保留

签名完成后持续保留，直到用户点击橡皮擦。

清除时每笔依次启动粒子消散，粒子从完整可见的笔画区域采样。整个过程需要与铅笔归位、阴影恢复及输入框重置协调。

清除完成后恢复输入功能，不增加重播按钮。

## 七、低动态模式与无障碍支持

### 7.1 系统动态偏好

低动态模式完全跟随操作系统的 `prefers-reduced-motion` 设置，不增加网页模式切换控件。

系统需要实时监听偏好变化，并由统一协调层处理。

### 7.2 动态切换

切换到低动态模式时：

- 保留已完成笔画和当前书写进度。
- 立即降低能够安全调整的粒子、阴影等非核心效果。
- 当前动作保持原有进度并安全完成。
- 后续动作采用低动态参数。
- 笔尖、完整笔画遮罩和阴影继续共享同一动作进度。

如果无法保证同步，则取消书写、清理临时资源、恢复铅笔和阴影初始状态，保留原文并允许重试。

### 7.3 无障碍语义

补齐输入框和按钮的语义标签、禁用状态及屏幕阅读器播报。

预检开始、预检失败、书写完成、清除完成和异常恢复都应得到适当通知。

不增加可见控件，不随意移动键盘焦点，并避免重复播报。

## 八、缓存、异常恢复与资源管理

### 8.1 缓存策略

建立可配置容量预算的 LRU 缓存，分别管理：

- 原始数据分片。
- 解析后的字形。

当前书写任务正在使用的数据必须受到保护，不能因缓存淘汰而失效。

缓存预算根据真实内存测量确定。

### 8.2 组件卸载与异步任务

组件卸载或离开页面时，由统一协调层：

- 取消动画。
- 使未完成的异步任务失效。
- 清理临时粒子、遮罩和渲染资源。
- 释放不再使用的资源。
- 保留仍可复用的合格字形缓存。

### 8.3 不可恢复异常

书写异常时停止时间线，取消未完成任务，清理不完整墨迹与临时粒子，恢复铅笔和阴影初始状态。

保留原文和已经验证的字形缓存，恢复输入功能并提示错误。

清除动画发生异常时，强制完成清理，确保界面可以再次书写。

## 九、开发阶段与实施顺序

### 阶段一：工程基线与安全分支

1. 检查 Git 状态、当前分支和未提交修改。
2. 如果项目尚未使用 Git，先建立安全的版本管理方案。
3. 建立独立中文功能分支。
4. 记录现有英文测试、性能基线和关键视觉截图。
5. 确认当前组件结构、坐标映射、GSAP 时间线和资源生命周期。
6. 冻结已有英文功能的回归基线。

**阶段产出：** 工程审计报告、分支与提交计划、现有功能基线。

### 阶段二：字形数据源对比与原型

1. 比较两套候选数据源及许可条件。
2. 选择覆盖不同技术难点的代表性汉字。
3. 比较完整轮廓、中线、笔顺、转换成本及动画效果。
4. 建立统一数据格式和质量指标。
5. 完成中文原型，验证完整笔画显现、铅笔运动和共享坐标。
6. 校准同步误差、动画时序和性能指标。

**阶段产出：** 数据源选型报告、统一数据格式、原型测试报告和初步验收标准。

### 阶段三：离线数据转换与质量流水线

1. 建立数据源解析、坐标归一化和标准格式转换工具。
2. 实现全量自动检查和异常隔离。
3. 建立自动修复、修复复验及人工复核机制。
4. 实现主来源优先、风险分级备用来源比较。
5. 建立候选评分、许可追踪和版本记录。
6. 生成字形图集及质量报告。

**阶段产出：** 可重复执行的数据处理流水线、字形质量数据库、异常清单和数据来源记录。

### 阶段四：中文引擎与统一书写计划

1. 实现中文字形加载与解析。
2. 建立完整轮廓和中线轨迹的匹配机制。
3. 建立中文、英文、数字和标点的统一书写计划接口。
4. 扩展 `SignatureController.js`，保留原有英文执行机制。
5. 实现中文完整笔画遮罩、3D 铅笔同步、抬笔和阴影动作。
6. 建立混合时序与异常恢复逻辑。

**阶段产出：** 中文引擎、统一书写计划、动画集成测试及同步测量报告。

### 阶段五：输入、排版和性能优化

1. 实现响应式 textarea 和 IME 兼容提交逻辑。
2. 实现字形独立排版参数和统一坐标契约。
3. 实现中文标点断行及手动换行保留。
4. 建立文本长度、行数、笔画规模和动画时长预检。
5. 实现本地分片、按需加载及 LRU 缓存。
6. 实现低动态模式、屏幕阅读器状态播报和异常恢复。
7. 根据实际设备数据校准性能预算及自适应渲染参数。

**阶段产出：** 完整交互流程、性能测试报告和输入排版回归测试。

### 阶段六：字库扩展与全面验收

1. 批量处理目标汉字。
2. 对全部候选字形执行自动质量检查。
3. 对异常、复杂和修复失败的字形进行备用来源比较。
4. 对代表性及复杂字形执行动画抽测。
5. 对自动检查通过的字形进行抽样审计。
6. 完成完整图集审查和异常复验。
7. 统计目标字数、实际覆盖数、合格数及暂不支持数。
8. 执行英文回归、故障注入、跨浏览器、真实设备和生产构建验收。

**阶段产出：** 正式字形分片、完整测试证据、验收报告及发布门禁结论。

### 阶段七：发布与合并

1. 确认全部正式发布门禁通过。
2. 检查版本、许可、数据来源和构建产物。
3. 检查 Git 工作区和分支提交记录。
4. 复核生产构建及部署环境行为。
5. 只有全部门禁通过后，才考虑将中文功能分支合并至主分支。

**阶段产出：** 可发布版本、最终验收报告、提交记录和发布说明。

## 十、自动化测试与验收体系

### 10.1 测试覆盖范围

- 字形加载、解析、缓存命中及缓存淘汰。
- 全部目标字形的自动质量检查。
- 轮廓与中线匹配、笔顺、轨迹连续性和排版参数。
- 笔尖同步误差与完整笔画动态显现。
- 中英文混排、数字、标点、空格及多行文本。
- 输入法组合输入、桌面键盘和手机提交行为。
- 预检失败、书写异常、清除异常及组件卸载。
- 动态偏好实时切换和安全降级。
- 低动态模式下的书写、清除及异常恢复。
- 桌面、手机、不同设备像素比及窗口缩放。
- 内存、帧率、动画时长和长文本性能。

### 10.2 故障注入

主动模拟加载失败、预检失败、书写中断、抬笔异常、粒子清除失败和组件卸载等情况。

每种故障都必须检查：

- GSAP 时间线状态。
- 墨迹与粒子资源。
- 铅笔和阴影位置。
- 异步任务有效性。
- 输入框状态和原文保留。
- 缓存完整性。
- 清理后的再次书写能力。

### 10.3 浏览器验收分级

| 环境 | 验收要求 |
|---|---|
| 桌面 Chrome/Chromium | 完整自动化、同步误差、故障注入和生产构建验收 |
| Edge、Firefox、WebKit | 关键功能回归、输入、排版、书写、清除及低动态行为 |
| iOS Safari | 真实设备输入法、触摸、WebGL、缩放和低动态验证 |
| Android Chrome | 真实设备输入法、触摸、WebGL、缩放和低动态验证 |

Playwright 的模拟结果不得替代真实设备验证。未完成相应测试的环境不得标记为已完整验收。

## 十一、性能预算与自适应渲染

建立可测量的性能预算，通过原型和真实设备测试校准阈值。

重点测量：

- 字形加载和预检时间。
- 书写计划生成时间。
- 动画帧率和帧时间分布。
- 笔尖与中线的同步误差。
- 动态遮罩的显现质量。
- 缓存占用和峰值内存。
- 清除动画的完成时间。
- 长文本的预估与实际执行时长。

设备性能不足时，可以降低非核心粒子、阴影和辅助渲染质量，但不得牺牲真实笔顺、完整笔画显现和笔尖同步。

具体数值阈值必须来自实际测试，不能在没有测量证据时直接宣布达标。

## 十二、正式发布门禁

以下条件必须全部满足，才能宣布正式版本通过验收。

### 字库门禁

- 目标约 3500 个一级常用简体汉字。
- 实际合格字形数量达到正式目标。
- 全部正式字形通过自动质量检查。
- 异常字形已修复复验、人工复核或隔离。
- 数据来源、版本和许可记录完整。
- 完整图集审查和代表性动画抽测完成。

### 功能门禁

- 现有英文测试全部通过。
- 中文笔画轮廓、中线和笔顺符合质量标准。
- 笔尖同步误差达到校准后的正式阈值。
- 输入预检、混排、自动换行和手动换行符合要求。
- 低动态模式、清除、异常恢复和再次书写流程正常。
- 屏幕阅读器状态播报和输入法行为符合已确定的交互规范。

### 工程门禁

- 全流程故障注入测试通过。
- 缓存、资源清理和异步任务管理通过检查。
- 性能预算及自适应渲染达到冻结的验收标准。
- 跨浏览器关键回归和要求的真实设备测试完成。
- 生产构建和发布检查通过。
- 数据许可、版本追踪和来源记录完整。

### 发布报告

每次正式验收必须输出：

1. JSON 机器可读报告。
2. Markdown 或 HTML 验收报告。
3. 关键帧截图、视觉差异图和失败证据。
4. 字形目标数、实际覆盖数、合格数和暂不支持数。
5. 测试环境、执行时间、版本和质量指标。
6. 每项发布门禁的通过或失败状态。
7. 未解决问题、人工复核结果和发布结论。

任何硬性门禁失败，都必须明确标记为未通过，不得通过降低标准、删除失败证据或将未验证字形计入合格数量来满足目标。

## 十三、最终交付清单

项目完成时应具备以下交付物：

- 中文书写引擎及独立字符引擎接口。
- 统一书写计划和扩展后的 `SignatureController.js`。
- 字形数据源选型报告及许可记录。
- 离线标准化转换和质量检查工具。
- 合格的正式本地字形分片。
- 自动修复、异常隔离和人工复核记录。
- 完整的输入、排版、动画和清除交互。
- 自动化测试、故障注入和浏览器回归测试。
- 同步误差、性能和视觉回归报告。
- JSON 与 Markdown/HTML 验收报告。
- 独立 Git 功能分支、阶段提交记录和最终发布说明。

## 十四、项目完成标准

本项目的完成标准不是“网页已经能够显示中文”，也不是“3500 个字符已经生成”。

真正的完成标准是：

**在不破坏现有英文功能的前提下，建立一套能够可靠加载、排版、逐笔书写和清除中英文混合文本的系统；所有正式字形均具有可追溯的数据来源、经过验证的笔画与中线关系，并通过同步、性能、异常恢复、浏览器和生产环境验收。**

开发期间可以逐批使用已经合格的字形进行验证，但正式发布必须达到约 3500 个合格简体汉字的目标，并通过全部规定的质量门禁。

在此之前，项目只能标记为开发中、阶段验收通过或正式发布未通过，不得将阶段性成功误认为完整交付。
